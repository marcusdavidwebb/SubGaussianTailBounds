# Machine-checked contribution records

Each improvement has one immutable JSON file in `records/`. The two
`baseline-*.json` files describe the initial hybrid-verified result. Copy
[`templates/improvement.json.example`](templates/improvement.json.example)
to `records/YOUR-ID.json`, replace every example value, and add the proof,
verification note and Lean module it names. The example numbers are an
illustration of the format; **no improvement is asserted or proved by the
template**.

A record contains all four exact constants, a `general` (all `K ≥ 1`) or
`one` (`K = 1`) scope, named contributors, an ISO date and an `improves`
predecessor of the same scope. At least one constant must strictly decrease.
Use `comparison: "pareto"` if none increases, or `"tradeoff"` if another
increases. Supported exact expressions are positive integers, positive
rationals such as `"96/25"`, and square roots such as `"sqrt(2)"`. JSON
floating-point numbers and arbitrary Lean expressions are rejected.

Proofs go in `proofs/` as editable `.md`, `.tex` or `.rst` source. A PDF alone
does not qualify. Put a verification note in `verification/` describing the
analytic changes, all finite premises, their checker correspondence, reused
work, limitations and attribution. Add the record ID to both
`../CONTRIBUTIONS.md` and `../CONSTANTS.md`.

## Lean contract

New modules belong in `lean/SingularValueBounds/KL/Contributions/`. Append
their imports to `lean/SingularValueBounds.lean`. Existing mathematical
modules, exact checkers and accepted records are preserved. Improvements
therefore cannot weaken the original theorem, assumptions or certificate
predicates by editing their definitions. Framework extensions need a
separate reviewed maintenance PR.

The record's `lean_theorem` is a fully qualified declaration accepting
arguments in this order:

```lean
theorem verified {Ω : Type*} [MeasurableSpace Ω]
    (μ : Measure Ω) [IsProbabilityMeasure μ]
    (hcert : FinalCertificateConditions)
    (hnum : NumericalCertificateConditions newData) :
    TheoremKL μ improvedConstants := by
  -- Supply the completed analytic proof.
```

For `scope: "one"`, replace the conclusion by the explicit endpoint target:

```lean
∀ (m n : ℕ) [NeZero n], n ≤ m →
  ∀ (X : Fin m → Ω → Fin n → ℝ),
    iIndepFun X μ → (∀ i, CentredIsotropic μ (X i)) →
    (∀ i, SubGaussianMGF μ (X i) 1) →
    ∀ t : ℝ, 0 ≤ t → TailBounds μ X improvedConstants 1 t
```

The generated CI target contains the **literal quartet from the JSON record**
and the original row assumptions. Lean must accept
`exact Your.Namespace.verified μ hcert hnum` at that target. Definitional
equality must identify the contributor's constants and data with the
generated literals. CI audits the resulting theorem's transitive axioms;
only `propext`, `Classical.choice` and `Quot.sound` are allowed. Neither an
extra analytic premise nor `sorry` can discharge the target. The complete
existing Lean build and baseline axiom audit also run.

`hcert` is the unchanged eleven-field baseline bundle. The record must name
the exact existing checker mapping for **every field**, including unchanged
fields. These programs all run again. When no additional finite premises
are needed, set `extra_certificates: null` and define `newData` as `[]`.
The theorem can ignore that empty-data argument.

## Additional finite certificates

To add new finite rational premises, set:

```json
"extra_certificates": {
  "path": "contributions/certificates/YOUR-ID.json",
  "description": "Which scalar conditions the new analytic argument uses"
}
```

The file contains explicitly enumerated comparisons, for example:

```json
[
  {
    "family": "new-scalar-bound",
    "checks": [
      {"relation": "le", "lhs": "1/2", "rhs": "2/3"},
      {"relation": "eq", "lhs": "3/4", "rhs": "3/4"}
    ]
  }
]
```

The trusted validator evaluates these comparisons using Python's exact
`Fraction` arithmetic. It emits the same ordered comparisons as Lean
`CertificateData`, for example:

```lean
def newData : CertificateData :=
  [("new-scalar-bound", [
    ArithmeticCheck.le (1 / 2 : ℚ) (2 / 3 : ℚ),
    ArithmeticCheck.eq (3 / 4 : ℚ) (3 / 4 : ℚ)])]
```

Lean must derive the full tail theorem from `NumericalCertificateConditions
newData` and the baseline bundle. A custom Python program saying that a
theorem is true does not establish a new premise. Large certificates may
be generated by contributor scripts, but their explicit data must be
committed and checked by this interface. More expressive certificate
interfaces require a separately reviewed framework extension. Existing
baseline checker correspondence retains its documented hybrid trust boundary.

## Run the checks

From this repository's root, with its pinned external Lean setup configured:

```sh
export PYTHONDONTWRITEBYTECODE=1
python3 scripts/check_contributions.py \
  --generate-lean /tmp/SubGaussianContributionTargets.lean
SVB_EXTRA_LEAN=/tmp/SubGaussianContributionTargets.lean ./lean/check_hybrid.sh
python3 -m unittest discover -s tests -v
```

For a PR, CI runs the validator from the **trusted base revision**, compares
the candidate to `--base-ref`, and compiles the generated file. Passing the
Python preflight alone does not establish the constants. CI rejects a PR
without a complete new record by default; the separate exact-commit
maintenance authorization described in `../CONTRIBUTING.md` cannot waive
an improvement's mathematical evidence. Publication metadata, framework
maintenance and ordinary prose corrections still receive the full hybrid
checks.
